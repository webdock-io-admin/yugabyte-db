# [#35783] DocDB: Size ThreadSafeObjectPool by the maximum CPU index

Refs: yugabyte/yugabyte-db#35783

## Problem

In a container with a floating CPU limit and cgroup-aware CPU information
(e.g. Incus/LXD with lxcfs, `limits.cpu=4` on a 128-thread host), yb-master and
yb-admin crash with SIGSEGV at address 0 on their first RPC, in
`yb::ThreadSafeObjectPool<...>::Take()` called from `yb::Trace::GetAndInitArena()`.
It happens whenever a thread runs on a host CPU id that is >= the number of
CPUs the container sees. Pinning the container to CPUs `0..N-1` avoids it.

## Cause

References are to upstream master 62a4ac7139.

- `src/yb/util/object_pool.h:207` sizes the per-CPU pools with
  `base::RawNumCPUs()` (`src/yb/gutil/sysinfo.cc:437`). That is
  `std::thread::hardware_concurrency()` (`sysinfo.cc:408`), the number of
  online CPUs. Under lxcfs that is the container's limit, e.g. 4.
  Correction: our issue #35783 said "processors in `/proc/cpuinfo`"; the
  count actually comes from `hardware_concurrency()`, as #33068 explains.
  The mechanism is the same.
- `Take()` and `Release()` (`:224`, `:233`) index the pools with
  `GetCPU()` = `sched_getcpu()` (`:245`). That returns the host CPU id, e.g. 80.
- The `DCHECK_LT(cpu, pools_.size())` (`:246`) is compiled out in release
  builds, so `pools_[80]` reads past the vector and the garbage
  `boost::lockfree::stack` makes the call jump to 0.

Other per-CPU structures already size by the maximum CPU index:
`PerCpuRwMutex` (`src/yb/util/locks.h:179`, `n_cpus_ = base::MaxCPUIndex() + 1`)
and the clockbound clock (`src/yb/server/clockbound_clock.cc:189`).
`MaxCPUIndex()` reads `/sys/devices/system/cpu/present`
(`src/yb/gutil/sysinfo.cc:171`), which is 0-127 inside the container in the
report. I found no other user of `sched_getcpu()` that indexes an array sized
by `RawNumCPUs()`.

## Fix

`src/yb/util/object_pool.h`:

- The constructor sizes the pools by
  `std::max(base::RawNumCPUs(), base::MaxCPUIndex() + 1)`, as `PerCpuRwMutex`
  does. Every CPU id `sched_getcpu()` can return then has its own pool.
- `GetCPU()` uses the new `object_pool_internal::PoolIndexForCpu(cpu, num_pools)`.
  It returns the CPU id for in-range ids and maps out-of-range ids (`cpu % num_pools`)
  and a failed `sched_getcpu()` (`-1`, hashed thread id, as
  `clockbound_clock.cc` does) to a valid pool. So an unexpected id can no
  longer index out of bounds, even if `/sys/devices/system/cpu/present` were
  virtualised as well. This replaces the `DCHECK_LT`.
- `<thread>` is now included on all platforms (needed for the fallback).

macOS is unchanged (it already hashes the thread id).

## Tests run

- New tests in `src/yb/util/object_pool-test.cc`:
  - `TestObjectPool.PoolIndexForCpu`: in-range ids map to themselves; host
    ids 80 and 123 with 4 pools and `-1` map to an index < 4.
  - `TestObjectPool.ThreadSafePoolOnEveryCpu` (Linux): for every CPU in the
    process's affinity mask, a thread pinned to that CPU takes, releases and
    takes again. It checks that `sched_getcpu()` returns the pinned CPU and
    that the object is reused, so each CPU has its own pool. It also asserts
    `MaxCPUIndex() + 1 >= CPU_COUNT(affinity)`.
  - Neither test reproduces the container mismatch on a normal host, where
    the online CPU count and `present` agree. The first test covers the
    out-of-range mapping, and the sizing change is covered by the harness below.
- Standalone harness (outside the yb build, g++ 15.2, `-std=c++20 -Wall
  -Wextra -Werror -fsanitize=address,undefined`): it compiles
  `PoolIndexForCpu` copied verbatim from the patch and simulates the issue's
  numbers (4 CPUs listed, `present` 0-127, host CPU ids 23, 80, 119, 122, plus
  0, 3, -1). With the old sizing (4), ids 23/80/119/122 and -1 are out of
  bounds. With the new sizing (128), each id >= 0 gets its own pool (index ==
  id), -1 gets a valid index, and all ids stay < 4 if only 4 pools existed.
  Result: OK, no sanitizer findings.
- yb build and `util_object_pool-test`: see below.
